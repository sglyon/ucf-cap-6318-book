Introduction¶

  • So far we’ve explored individual AI agents and how to augment them with external knowledge

  • But many of the most interesting complex systems emerge from interactions between multiple entities

  • Recall from Week 6-7: the Schelling model showed how simple local interactions create surprising aggregate patterns

  • From Week 8: game theory taught us that outcomes depend not just on individual actions, but on strategic interactions

  • Today we extend these ideas to AI agents: what happens when multiple LLM-powered agents communicate and collaborate?

  • We’ll discover that emergent collaboration can solve problems that single agents cannot

From Single Agents to Multi-Agent Systems¶

The Limits of Individual Agents¶

  • A single LLM agent, no matter how sophisticated, faces fundamental constraints:

    • Context window limits: Can only “remember” the last N tokens

    • Single perspective: One prompt, one approach, one set of biases

    • No self-correction: Limited ability to catch its own mistakes

    • Generalist burden: Must be good at everything simultaneously

Multi-Agent Advantages¶

  • Multiple agents working together can overcome these limitations:

    • Specialization: Different agents for different tasks (like division of labor in economics)

    • Diverse perspectives: Multiple approaches to the same problem

    • Error correction: Agents can critique and improve each other’s outputs

    • Scalability: Distribute work across parallel agents

Connection to Course Themes¶

  • ABMs: Like Schelling agents, AI agents have simple rules (their prompts) but complex interactions

  • Networks: Agents form communication networks with different topologies

  • Game Theory: Strategic interaction between agents pursuing different objectives

  • Emergence: Coordination patterns emerge without central planning

Agent Communication Protocols¶

Message Passing Architecture¶

  • How do AI agents communicate?

  • In traditional ABMs (like Schelling), agents interact through shared environment state

  • In AI multi-agent systems, agents typically use explicit message passing

  • Each message contains:

    • Sender: Which agent created the message

    • Content: The actual text/data

    • Metadata: Timestamp, message type, intended recipient(s)

Conversation Structure¶

  • We need to decide on a conversation flow:

    1. Sequential: Agents take turns in fixed order (round-robin)

    2. Dynamic: Next speaker chosen based on context or rules

    3. Broadcast: One agent speaks to all others

    4. Selective: Agents choose who to respond to

  • For today, we’ll focus on sequential and dynamic patterns

Agent Type¶

  • Now we define our AI Agent

  • Unlike Schelling agents (which had fixed rules), our agents are defined by:

    • Role: What perspective or specialty they have

    • System prompt: Instructions that shape their behavior

    • Model: Which LLM they use (we’ll default to Claude)

    • Memory: Their conversation history

@dataclass
class AIAgent:
    role: str
    system_prompt: str
    model: str = "claude-haiku-4-5"
    memory: list[Message] = field(default_factory=list)
    api_key: str = field(default_factory=lambda: os.environ.get("ANTHROPIC_API_KEY", ""))

    # Custom repr to hide the API key
    def __repr__(self):
        masked_key = f"***{self.api_key[-4:]}" if len(self.api_key) > 8 else "***"
        prompt_preview = (
            self.system_prompt[:50] + "..."
            if len(self.system_prompt) > 50
            else self.system_prompt
        )
        return (
            f'AIAgent(role="{self.role}", '
            f'system_prompt="{prompt_preview}", '
            f'model="{self.model}", '
            f'memory={len(self.memory)} messages, '
            f'api_key="{masked_key}")'
        )

Agent Response Function¶

  • This function sends a message to an agent and gets its response

  • It’s similar to the API call from L.A1.01, but now includes conversation history

def get_response(agent, new_message):
    """Send a message to an agent and get its response."""
    # Build conversation history for API
    messages = []

    # Add history
    for msg in agent.memory:
        role = "assistant" if msg.sender == agent.role else "user"
        messages.append({"role": role, "content": msg.content})

    # Add new message
    messages.append({"role": "user", "content": new_message})

    # Prepare API request
    headers = {
        "x-api-key": agent.api_key,
        "anthropic-version": "2023-06-01",
        "content-type": "application/json",
    }

    body = {
        "model": agent.model,
        "max_tokens": 1024,
        "system": agent.system_prompt,
        "messages": messages,
    }

    # Make API call
    response = requests.post(
        "https://api.anthropic.com/v1/messages",
        headers=headers,
        json=body,
    )

    # Parse response
    result = response.json()
    content = result["content"][0]["text"]

    # Store in memory
    agent.memory.append(Message("user", new_message))
    agent.memory.append(Message(agent.role, content))

    return content

Running a Conversation¶

  • Now we’ll orchestrate a multi-turn conversation

  • The researcher proposes ideas, the critic responds, and this continues for several rounds

def run_conversation(agent1, agent2, initial_prompt, turns=3):
    # Start with initial prompt to first agent
    current_message = initial_prompt

    print("=" * 60)
    print("Starting conversation...\n")

    for turn in range(turns):
        # Agent 1 responds
        print(f"\n[{agent1.role}]")
        response1 = get_response(agent1, current_message)
        print(response1)

        # Agent 2 responds
        print(f"\n[{agent2.role}]")
        response2 = get_response(agent2, response1)
        print(response2)

        current_message = response2
        print("\n" + "-" * 60)
# Run the conversation
run_conversation(
    researcher,
    critic,
    "Propose a hypothesis about how weak ties in social networks affect information spread.",
    3,
)

[Researcher]

**Hypothesis:** Weak ties accelerate the spread of novel information across network clusters, but strong ties determine whether that information is *adopted and acted upon*—suggesting that viral reach and behavioral change require different tie strengths at different stages.

**Testable prediction:** Information shared through weak ties reaches 3x more people in the first week, but individuals who ultimately change behavior based on that information are 5x more likely to have learned it through strong ties, creating a two-stage diffusion process.

[Critic]

**Strengths:** You've identified a genuinely interesting dynamic—separating *reach* from *adoption*—and the directional predictions are specific enough to test.

**Critical weaknesses:**

1. **Causality confusion:** Your prediction conflates correlation with mechanism. People might adopt through strong ties *because* they're already predisposed to trust those people, not because tie strength *causes* adoption. Did the strong tie convince them, or did they seek out strong ties specifically to validate already-formed intentions? You need a design that isolates tie strength from selection bias.

2. **Missing mechanism for weak ties:** Why would weak ties be 3x *better* at spread if they're *worse* at adoption? If weak ties only reach people unlikely to act, calling this "acceleration" undersells the problem—it's just volume without conversion. What makes those 3x people worth reaching if 5x fewer convert?

3. **Vague operationalization:** How do you measure "ultimately changed behavior"? Stated intention? Observable action? Time lag? Without clarity, you risk selecting weak-tie examples that happened to reach early adopters (who'd adopt anyway) and strong-tie examples linked to genuine behavioral change.

**Suggestion:** Reformulate as *conditional* prediction: "Strong ties accelerate adoption *conditional on* weak-tie exposure creating initial awareness," then experimentally vary tie type while holding information identical.

[Researcher]

You've caught something crucial—I was treating correlation as mechanism and glossing over why weak ties matter if they don't convert.

**Revised hypothesis:** Weak ties are *efficient awareness-raisers* specifically because they span structural holes between groups with *different adoption barriers*; strong ties only accelerate adoption within groups that already share the barrier-lowering conditions (trust, resources, cultural fit), so weak ties appear slower but are actually necessary for reaching populations where strong-tie adoption would never occur.

**Better operationalization & test design:** 
- Measure "adoption barriers" first (cost, social risk, knowledge required)
- Randomly expose people to identical information via weak vs. strong ties
- Track: (1) awareness within 48 hours, (2) stated intent within 1 week, (3) actual behavior within 30 days, *stratified by barrier type*
- Predict: weak ties outperform on awareness in high-barrier groups; strong ties outperform on adoption in low-barrier groups—not because strong ties convince better, but because they only reach people for whom adoption was already feasible

This dodges the causality trap by testing *conditional effectiveness* rather than claiming tie strength drives conversion universally. And it explains why weak ties matter: they're not worse at conversion, they're reaching entirely different populations.

Does this reframe address the selection bias and mechanism problems you identified?

[Critic]

**Much stronger.** You've flipped from claiming tie strength has universal effects to claiming it has *conditional* effects—and you've made the stratification explicit, which lets you test mechanism rather than assume it.

**Remaining vulnerabilities:**

1. **Randomization feasibility:** "Randomly expose via weak vs. strong ties" is mechanistically tricky—how do you force someone to learn from a weak tie they don't naturally consult? If you engineer artificial weak-tie exposures, you've lost ecological validity (real weak ties carry different social friction, motivation to transmit, perceived credibility). You need to either justify the artificial setup or pivot to natural experiments (e.g., comparing organically formed weak-tie exposures across barrier groups).

2. **Barrier measurement endogeneity:** If you measure adoption barriers *before* exposure, people might rationalize barriers post-hoc based on which tie informed them ("I didn't adopt because I lack resources" vs. "I didn't adopt because my strong tie didn't convince me"). Consider measuring barriers independently, or use pre-existing barrier profiles (e.g., income-stratified groups with known resource constraints).

3. **"Already feasible" is post-hoc:** Your prediction hinges on "strong ties only reach people for whom adoption was already feasible." But this becomes unfalsifiable if you classify non-adopters as "not feasible" after the fact. Pre-specify what makes someone feasible (e.g., income >X, prior knowledge score >Y) to avoid retrofit logic.

**Bottom line:** The conditional framing is sound, but test design must nail whether weak ties *create* awareness in hard-to-reach groups or just *happen to* reach them.

[Researcher]

You're right—I've moved the theoretical problem without solving the empirical one. Let me rebuild from design constraints.

**Revised approach:** Use a natural experiment where information spreads through *organizational hierarchies* (e.g., workplace safety practices, software adoption). Weak ties = cross-departmental connections; strong ties = within-department. Pre-specify barrier profiles using *objective* criteria (department budget, equipment age, prior training completion rates), then measure: (1) *when* each group first encounters the information (via timestamped communication logs), (2) *which tie type* transmitted it, (3) adoption timing. This avoids artificially forcing exposures while capturing natural weak-tie paths.

**Falsifiability safeguard:** Pre-register that "feasible for adoption" means: department has required resources (equipment, time allocation) *documented before exposure*. If high-barrier departments adopt equally fast via strong vs. weak ties, the conditional hypothesis fails. If weak ties reach low-barrier departments first but strong ties dominate adoption even there, the mechanism isn't barrier-removal—it's something else (credibility, social pressure).

**The remaining honest gap:** This design can show *correlation* between tie type and adoption timing within barrier groups, but can't definitively separate "weak ties enabled adoption in hard-to-reach groups" from "weak ties just happened to reach people already primed to adopt." Only a randomized trial could isolate mechanism—but you've correctly flagged that randomization kills ecological validity. So the trade-off is explicit: natural experiments buy realism, lose causal certainty.

Does pre-registration + objective barriers tighten this enough, or is the design still underbaked?

[Critic]

**Honest assessment: you're at the pragmatic limit, not underbaked—but you need to *name the residual uncertainty* in your claims.**

Pre-registration + objective barriers *do* tighten things meaningfully:
- You eliminate post-hoc barrier classification and retrofit logic
- Timestamped logs + tie-type metadata beat self-reported data
- Falsifiable predictions (equal adoption across tie types = hypothesis breaks)

**But the core causal gap remains unfillable without intervention:** Even with perfect correlation data showing weak ties reach high-barrier departments first and those departments later adopt, you still can't rule out: (1) weak ties happened to reach the *one person in that department already motivated to push adoption*, (2) weak ties' slower transmission time allowed barriers to lower organically (budget approval, equipment arrived) before strong-tie adoption attempts, or (3) weak ties' *outsider status* made ideas seem safer precisely *because* they weren't social pressure from peers.

**You have three honest moves:**

1. **Reframe as mechanism-agnostic prediction:** "Weak ties correlate with awareness in high-barrier groups; strong ties correlate with adoption—mechanism TBD." Less satisfying theoretically, but true to the data.

2. **Add auxiliary tests** (qualitative interviews post-adoption, survey on *why* people adopted) to triangulate mechanism—won't prove it, but can eliminate some alternatives.

3. **Acknowledge the design is best suited to falsify the opposite claim** (that tie strength is universal), which is still valuable.

Pick your epistemic goal: correlation mapping, mechanism hints, or null-hypothesis killing?

Multi-Agent Coordination Patterns¶

AutoGen-Style Architecture¶

  • Microsoft’s AutoGen framework introduced several powerful patterns for multi-agent systems

  • Key idea: role-based specialization with structured handoffs

  • Common roles:

    • User proxy: Represents human input and approvals

    • Assistant: General problem solver

    • Executor: Runs code and reports results

    • Critic: Reviews and validates outputs

Sequential vs. Graph-Based Coordination¶

  • Sequential: A → B → C → D (like an assembly line)

    • Simple to implement and reason about

    • Limited flexibility

  • Graph-based: Agents can call each other based on conditions

    • More flexible and powerful

    • Can create cycles (debate loops) or branches (conditional paths)

    • Requires careful design to avoid infinite loops

Connection to Networks¶

  • Multi-agent coordination is a directed graph!

  • Nodes = agents, Edges = possible communications

  • Topology affects performance:

    • Chain: Sequential processing

    • Star: Central coordinator (hub)

    • Fully connected: Any agent can talk to any other

    • Hierarchical: Manager-worker structure

The Scenario¶

  • Multiple communities need coordinated response

  • Resources are limited and must be allocated efficiently

  • Our AI agents will:

    • Assess the situation from different perspectives

    • Coordinate resource allocation

    • Adapt to new information

)

Multi-Agent Response Protocol¶

  • We’ll implement a coordination protocol:

    1. Initial assessment: Each specialist evaluates the situation independently

    2. Discussion phase: Specialists share perspectives and debate priorities

    3. Synthesis: Analyst integrates inputs and proposes action plan

    4. Validation: Team reviews and refines the plan

  • This mirrors real incident command structures but without rigid hierarchy

def disaster_response_round(scenario, team):
    print("\n" + "=" * 70)
    print("DISASTER SCENARIO")
    print("=" * 70)
    print(scenario)
    print()

    # Phase 1: Independent assessments
    print("\n" + "=" * 70)
    print("PHASE 1: INDEPENDENT ASSESSMENTS")
    print("=" * 70)

    assessments = {}
    for agent in team[:-1]:  # All except analyst
        print(f"\n[{agent.role} Assessment]")
        assessment = get_response(
            agent,
            f"Given this scenario: {scenario}\n\nProvide your assessment from your area of expertise.",
        )
        print(assessment)
        assessments[agent.role] = assessment

    # Phase 2: Synthesis
    print("\n" + "=" * 70)
    print("PHASE 2: SITUATION ANALYSIS AND RECOMMENDATIONS")
    print("=" * 70)

    # Build summary for analyst
    summary = "Team assessments:\n\n"
    for role, assessment in assessments.items():
        summary += f"{role}: {assessment}\n\n"
    summary += "Based on these inputs, what are your top 3 recommended immediate actions?"

    print("\n[Analyst Recommendations]")
    recommendations = get_response(team[-1], summary)
    print(recommendations)

    # Phase 3: Quick validation round
    print("\n" + "=" * 70)
    print("PHASE 3: TEAM VALIDATION")
    print("=" * 70)

    for agent in team[:-1]:
        print(f"\n[{agent.role} Response]")
        validation = get_response(
            agent,
            f"The analyst recommends: {recommendations}\n\nBriefly respond: any critical concerns or support?",
        )
        print(validation)

    return recommendations

Game-Theoretic Analysis of Multi-Agent Systems¶

From ABMs to Strategic Agents¶

  • Recall the Schelling model: agents had fixed preference functions

  • AI agents are fundamentally different: they can reason about others’ behavior

  • This makes them strategic players in the game-theoretic sense

Coordination Games¶

  • Multi-agent AI systems often face coordination problems

  • Example: Which disaster area to prioritize?

    • If both medical and logistics focus on Island Community → waste resources

    • If they split effort optimally → better outcomes

    • Multiple equilibria possible (each area could be prioritized)

  • Communication helps select among equilibria

  • This is why our multi-agent protocol included explicit discussion phases

Mechanism Design for AI Agents¶

  • Question: How do we design prompts and protocols to achieve desired outcomes?

  • This is mechanism design applied to AI systems

  • Key considerations:

    1. Incentive compatibility: Each agent’s prompt should make truthful reporting optimal

    2. Information aggregation: How do we combine diverse perspectives?

    3. Termination: How do we ensure conversations conclude productively?

Example: Voting vs. Consensus¶

  • Two ways to make group decisions:

    • Voting: Each agent proposes action, majority wins (simple but can ignore minorities)

    • Consensus: Discussion until agreement (thorough but can be slow)

  • Our disaster protocol used a hybrid: discussion + analyst synthesis

  • This is a dictator game where the analyst has final say, but is informed by others

Voting Mechanism¶

  • Let’s implement a simple voting system for multi-agent decision making

  • Each agent votes for an option, and we tally results

def voting_decision(agents, question, options):
    print("\n" + "=" * 70)
    print("VOTING ROUND")
    print("=" * 70)
    print(f"Question: {question}")
    print("Options:", ", ".join(options))
    print()

    votes = {opt: 0 for opt in options}

    vote_prompt = f"""{question}

    Options: {", ".join(options)}

    Vote for ONE option and briefly explain why (1 sentence).
    Format your response as: VOTE: [option] - [reason]"""

    for agent in agents:
        print(f"\n[{agent.role}]")
        response = get_response(agent, vote_prompt)
        print(response)

        # Parse vote (simple string matching)
        vote_match = re.search(r"VOTE:\s*([^-\n]+)", response)
        if vote_match is not None:
            vote_text = vote_match.group(1).strip()
            for opt in options:
                if opt in vote_text:
                    votes[opt] += 1
                    break

    print("\n" + "=" * 70)
    print("RESULTS")
    print("=" * 70)
    for option, count in sorted(votes.items(), key=lambda x: x[1], reverse=True):
        print(f"{option}: {count} votes")

    winner = max(votes, key=votes.get)
    print(f"\nDecision: {winner}")
    return winner

Consensus Through Debate¶

  • Voting is fast but doesn’t capture nuance

  • Sometimes we need consensus - a decision everyone can support

  • Let’s implement a debate-to-consensus mechanism

def consensus_decision(agents, question, max_rounds=3):
    print("\n" + "=" * 70)
    print("CONSENSUS BUILDING")
    print("=" * 70)
    print(f"Question: {question}\n")

    # Initial proposals
    print("ROUND 1: Initial Proposals")
    print("-" * 70)
    proposals = []
    for agent in agents:
        print(f"\n[{agent.role}]")
        proposal = get_response(agent, f"{question}\n\nProvide your initial proposal and reasoning.")
        print(proposal)
        proposals.append(proposal)

    # Debate rounds
    for round_num in range(2, max_rounds + 1):
        print("\n" + "=" * 70)
        print(f"ROUND {round_num}: Discussion and Refinement")
        print("-" * 70)

        summary = "Previous proposals:\n" + "\n\n".join(
            f"{agents[i].role}: {proposals[i]}" for i in range(len(agents))
        )

        new_proposals = []
        for agent in agents:
            print(f"\n[{agent.role}]")
            response = get_response(
                agent,
                f"{summary}\n\nGiven these proposals, refine your position or indicate agreement with another proposal.",
            )
            print(response)
            new_proposals.append(response)
        proposals = new_proposals

    # Final consensus check
    print("\n" + "=" * 70)
    print("FINAL CONSENSUS")
    print("=" * 70)
    final_summary = "After discussion, the proposals are:\n" + "\n\n".join(
        f"{agents[i].role}: {proposals[i]}" for i in range(len(agents))
    )
    print(final_summary)

    return proposals

Emergent Behavior Analysis¶

What Makes Behavior “Emergent”?¶

  • Recall from the ABM money lecture that we didn’t specify that wealth followed a power law: that result emerged Emergence means system-level patterns not explicitly programmed

  • In Schelling model: segregation emerged from mild individual preferences

  • In our multi-agent system:

    • No agent knows the “correct” answer

    • No central controller dictating decisions

    • Coordination emerges from local interactions (conversations)

    • Better solutions than any individual agent could produce

Comparing to Traditional ABMs¶

Traditional ABM (Schelling)AI Multi-Agent System
Fixed rulesLearned behaviors
No reasoningExplicit reasoning
Implicit communication (environment)Explicit communication (messages)
Simple agents, complex patternsComplex agents, complex patterns
Deterministic (given rules)Stochastic (LLM sampling)

Sources of Emergence in AI Systems¶

  1. Prompt interpretation: Each agent interprets prompts slightly differently

  2. Stochastic sampling: LLMs don’t give identical outputs every time

  3. Conversation dynamics: Order of speakers affects outcomes

  4. Information aggregation: Synthesis creates novel insights

  5. Feedback loops: Later responses build on earlier ones

Connection to Collective Intelligence¶

Wisdom of Crowds¶

  • Classic result (Surowiecki, 2004): aggregated judgments often beat individual experts

  • Requires:

    1. Diversity: Different perspectives and information

    2. Independence: Agents form opinions without undue influence

    3. Decentralization: Local knowledge utilized

    4. Aggregation: Mechanism to combine judgments

  • Our multi-agent systems can achieve this:

    • Different prompts → diversity

    • Independent initial assessments → independence

    • Specialized roles → decentralized expertise

    • Analyst synthesis or voting → aggregation

Debate Improves Accuracy¶

  • Research shows LLMs are more accurate when they “debate” solutions

  • Debate surfaces hidden assumptions and errors

  • Multiple rounds allow error correction

  • Connection to game theory: Debate is a signaling game where agents reveal information

Practical Considerations¶

Cost Management¶

  • Multi-agent systems make many API calls

  • Example: 4 agents, 3 rounds, 2 messages per round = 24 API calls

  • At 0.003per1Kinputtokens,0.003 per 1K input tokens, 0.003per1Kinputtokens,0.015 per 1K output tokens (Claude Sonnet):

    • Average message: ~500 input tokens, ~200 output tokens

    • Cost per message: ~1.50+ 1.50 + ~1.50+ 3.00 = $4.50 per 1000 messages

    • Our example: ~$0.11 per scenario

  • Strategies to reduce cost:

    • Use smaller/cheaper models for simple agents

    • Cache common responses

    • Limit conversation rounds

    • Implement early stopping when consensus reached

Conversation Management¶

  • Infinite loops: Agents might talk forever without reaching decision

    • Solution: Maximum turn limits, explicit termination conditions

  • Off-topic drift: Agents might lose focus on original question

    • Solution: Regular reminders in prompts, moderator agent

  • Echo chambers: Agents might all converge to same view prematurely

    • Solution: Explicit “devil’s advocate” role, diversity requirements

Quality Control¶

  • How do we know if multi-agent outputs are good?

  • Evaluation approaches:

    1. Human review: Gold standard but expensive

    2. Automated metrics: Consistency checks, format validation

    3. Benchmark tasks: Test on known problems

    4. A/B testing: Compare multi-agent vs. single-agent outputs
